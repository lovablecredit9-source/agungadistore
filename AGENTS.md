
- Files imported from TanStack-based uploads use `@/lib/router-compat` (re-exports react-router-dom) and `@/lib/server-fn-compat`; server functions become edge functions (e.g. account-slots). Why: project stays on React Router + Vite.
- PIN checks go through `verify_account_pin` (DB) / `_shared/pin.ts` (edge) and `src/lib/pin.ts` (client); never compare `user_pins.pin_hash` inline. Why: PINs belong to the balance account, while visitor_ids differ per device, and inline checks rejected correct PINs.

- Only admins change ticket status; user rating/read/delete use owner-checked `ticket_user_action` / `ticket_user_message_action`; admin online from `admin_heartbeat`. Why: tickets are visitor-based, so browsers never write ticket rows directly.
- Checkout price protection: client sends `expectedPrices` per cart item to `seller-shop` checkout, which rejects with "Harga produk telah berubah" before `buyer_checkout` runs. Why: never charge a price the buyer did not see.
- Telegram stays one bot: `telegram-webhook` (user bot), `telegram-manage` (admin-only, never returns the token), and one delivery path `_shared/telegram.ts` `deliverTelegram` (preference check + `telegram_delivery_log` event_key idempotency) used by `telegram-notify`; new `notifications` rows reach it via DB trigger, browsers manage links only through owner-checked `telegram-link-direct`. Why: bot token and links were browser-readable and most events never reached Telegram.
- Currency mutators (`add_account_gems`, `add_account_credits`, balance consume/refund/bonus RPCs) are service-role only; browsers use `spend_account_gems` (deduct-only) and `claim_profile_reward` (atomic, capped). Every edge function must check the `add_account_gems` error before granting rewards, and gacha results (Mega Arena, Diamond Royale) are rolled server-side. Why: anon could previously mint Gems/balance and claim client-chosen prizes.
- Admin balance changes (deposit approval, topup, reset, correction) go through admin-checked RPCs `admin_approve_deposit` / `admin_adjust_balance`; never write `user_balances.balance` from the browser. Why: client copies of the balance were stale and could overwrite purchases made in between.
- Money/reward tables (`user_balances` insert, `streak_subscriptions`, `game_balance`, `lucky_draw_tickets`, `streak_active_boosters`, `seller_earnings`, `balance_login_history`) are written only by edge functions/RPCs; avatar uses `set_account_avatar`, own account id uses `my_active_user_balance_id`. Regression in `src/test/securityRegression.test.ts`. Why: open insert policies let anyone mint balance, memberships and account links.
- Admin-only edge function actions (`admin_*` actions, whole admin functions) must call `isAdminRequest` from `supabase/functions/_shared/admin.ts` (role check via `has_role`); never hardcode admin user IDs. Why: several functions let anyone ban users, mint vouchers/quests and grant Fire Pass.

- Directory rules live in `AGENTS.md` under: `src/components/` games, deposit, premium, music, confess, streak (purchases, Streak Shop, vouchers), admin, security (login history, logout/switch), posts (admin posts), wallet (membership cards), luck/royale.
- Pure rules shared by edge functions and Vitest live in `supabase/functions/_shared/` (`gem-order.ts` for Gem order totals/payment-source mirror of `gem_purchase_pay`, `admin-search.ts` for admin user search). Why: tests exercise the same code the server runs.
- Wallet identity: `auth_link` no email/admin link; `claim_link` links old wallets; payer via `_shared/wallet-identity.ts`; OAuth return needs `isSessionFromThisLogin`. Why: email/visitor_id/old sessions prove nothing.

- Supabase RPC builders are lazy: always await/then them (heartbeats use `send` in `useAdminOnline.ts`). Why: `void rpc()` never sent admin_heartbeat, so admin last seen stayed NULL.
- Sewa Bot Telegram: all money/expiry/slot/voucher logic lives in RPCs `bot_rental_purchase`/`bot_rental_quote`/`bot_rental_admin_extend`/`bot_rental_tick` (service-role only), reached via edge function `bot-rental`; bot tables have no browser grants and bot tokens are never returned. Runtime is Telegram webhook -> `bot-hook` interpreting the active version's `adistore-bot.json` (data only; user JS is never executed, Node ZIPs are reported incompatible); tokens AES-GCM encrypted via `_shared/bot-crypto.ts`. Why: no sandbox for arbitrary code on built-in runtime; never fake bot status or trust client prices.
